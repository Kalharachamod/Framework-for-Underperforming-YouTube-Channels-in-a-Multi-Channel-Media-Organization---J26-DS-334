# Component 1 collection design

Status: local design only; deployment and scheduled collection are disabled.
Prepared 2026-10-18. Official documentation checked on that date.
Revised 2026-10-20: see "2026-10-20 revision" at the end. Where it conflicts with
earlier sections (keys, budgets, bootstrap, refresh), the revision takes precedence.

## Scope and fixed boundaries

Use a separate `c1` schema in the existing Supabase project, with a dedicated
`c1_collector` login and PostgreSQL protocol access. No owner, service-role,
project secret API key, or shared database credential may be used by the collector.
No credential fallback is allowed. Existing `COMPONENT1_DB_URL`,
`component1_readonly`, shared code, Python statistics runner, research tables,
data, permissions, policies, and `research.schema_migrations` remain unchanged.

The current manifest at
`config/cohorts/component_1_derana_v0.1.0.proposed.json` remains proposal-only,
pending approval, and disabled. Its 18 channels are a proposed allowlist, not an
activation instruction. No historical statistics are copied.

The existing runner supplies behavioral requirements and synthetic fixtures;
it is not deployed into Edge Functions or given a writer. New collection code
must not import shared database writers, whose mappings target `research.*`.
The `c1` schema stays outside the exposed Data API schemas.

## Minimum schema

Use UUIDs generated by the application for operational identities, avoiding
sequence privileges. All foreign keys reference only `c1` objects. The initial
design supports one active cohort version at a time.

| Table | Primary/unique keys | Required content |
|---|---|---|
| `c1.cohorts` | PK `(cohort_id, version)` | Canonical manifest hash and channel allowlist; approval reference/by/at; `enabled=false`; approved budgets, schedule and retention-decision reference. Collector cannot change this table. |
| `c1.channels` | PK `(cohort_id, version, channel_id)` | Allowlisted channel inventory, source, admitted time, nullable metadata, uploads playlist, latest successful metadata timestamp. Bootstrap admission is distinguishable from a fresh API observation. |
| `c1.videos` | PK `(cohort_id, version, video_id)`; unique same columns plus `channel_id` for ownership references | Stable owning channel, admission source/time, inventory revision, nullable bootstrap metadata, publication time when known, latest successful metadata timestamp. FK to C1 channel. Ownership cannot change silently. |
| `c1.channel_stats_history` | PK `(cohort_id, version, channel_id, observed_at)` | Nullable subscriber/view/video counts, run and work-item provenance, canonical payload hash. |
| `c1.video_stats_history` | PK `(cohort_id, version, video_id, observed_at)` | Nullable view/like/comment counts, run and work-item provenance, canonical payload hash. |
| `c1.collection_runs` | PK `run_id`; unique `(cohort_id, version, scheduled_for)` | Manifest hash, frozen inventory revision/cutoff, phase, start/heartbeat/end, deadlines, budget counters, completion summaries and sanitized failure code. |
| `c1.collection_work` | PK `work_id`; unique `(run_id, work_key)` | Bounded batch or discovery-page task, selected IDs, phase/channel, input/output cursor, dispatch order, lease owner/expiry/fence, next retry time, attempts, bounded staged response, original observation timestamp/hash and outcome counts/IDs. Every row references a real run. |
| `c1.collection_coordination` | PK `(cohort_id, version)` | Operator-created singleton per cohort version; nullable active-run FK, lease owner/expiry/fence, inventory revision and rotating discovery start. No fake task/run identifiers. Collector can SELECT and update operational columns, but cannot INSERT or DELETE rows. |
| `c1.schema_migrations` | PK `version` | Independently reviewed C1 migration versions/checksums, applied by the deployment operator only. |

The work table combines checkpoints and collection outcomes to avoid separate
status/checkpoint tables. Do not store an unbounded run's IDs or responses in a
single row. Split tasks into at most 50 selected IDs or one playlist page.
Per-ID outcomes distinguish unavailable, invalid, failed/unconfirmed, and
unattempted. Inventory metadata is current state; history holds observations.

Use checked ID formats, timezone-aware `timestamptz`, nullable nonnegative
`bigint` metrics and monotonic inventory revisions. Handle JavaScript counts
without lossy Number conversion. Index video ownership, history entity/time,
work status/next-attempt, and run scheduled time/status. Avoid metadata such as
full descriptions unless a defined C1 feature needs it.

## Collector permissions

Deployment requires a separately authorized administrative actor; administrative
credentials are never stored in the Edge Function. A separate owner owns new C1
objects. The runtime role is LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE,
NOREPLICATION and NOBYPASSRLS, with no role memberships or grant options.

The runtime allowlist is:

| Object | Runtime permission |
|---|---|
| Existing database | `CONNECT` only as required to authenticate; no new CREATE/TEMP grant |
| Schema `c1` | `USAGE`, no `CREATE` |
| `c1.cohorts` | `SELECT` only |
| `c1.channels`, `c1.videos` | `SELECT`, `INSERT`; column-level `UPDATE` only for mutable metadata, latest-success timestamp and discovery state; no changes to IDs, cohort/version, ownership or original admission fields |
| Both C1 history tables | `SELECT`, `INSERT`; no `UPDATE` or `DELETE`. Trigger `c1.guard_history` also blocks UPDATE and TRUNCATE for every role, and DELETE outside a retention purge (see Monitoring and storage) |
| `c1.collection_runs` | `SELECT`, `INSERT`; column-level `UPDATE` for phase, heartbeat/end, counters and outcomes; immutable identity, schedule and cohort/hash |
| `c1.collection_work` | `SELECT`, `INSERT`; column-level `UPDATE` for cursors, response staging, leases, retries, attempt counters and outcomes; immutable task identity and selected-ID definition |
| `c1.collection_coordination` | `SELECT`; column-level `UPDATE` for active run, lease/fence, inventory revision and discovery rotation; no INSERT/DELETE |
| `c1.schema_migrations` | None |

No DELETE, TRUNCATE, REFERENCES, TRIGGER, ownership, schema creation, sequence
access or execution of new privileged routines is needed. Ordinary built-in
functions required for SQL expressions remain subject to the privilege audit.
No access to `research`, `annotation`, Vault, Cron, network-extension objects,
other application schemas, or migrations is granted to the collector.

Enable RLS on new C1 application tables, with role-specific SELECT/INSERT/UPDATE
policies matching this matrix and the enabled, approved cohort. Use both USING
and WITH CHECK where applicable. Do not grant public API roles access. Bootstrap
uses a separate reviewed importer/operator path while the cohort is disabled;
it does not relax scheduled-collector policies. Only new C1 ACLs, policies and
owner-specific defaults are configured. A permission shortfall never justifies
switching to a shared credential.

## Effective privilege gate before deployment

This is a future, explicitly authorized, read-only audit; no audit SQL was run
for this design. Capture evidence without credentials or source data:

1. Verify session_user/current_user are `c1_collector`. Inspect role attributes,
   recursive membership, inherited permissions and SET ROLE reachability,
   including membership options. NOINHERIT alone does not prevent SET ROLE.
2. Enumerate database/schema/table/column/sequence/routine ACLs, ownership and
   default ACLs, including PUBLIC and all reachable roles. Use PostgreSQL
   `has_database_privilege`, `has_schema_privilege`, `has_table_privilege`,
   `has_column_privilege`, `has_sequence_privilege`, `has_function_privilege`
   and `pg_has_role` alongside catalog inspection. A missing explicit grant is
   not proof of denied effective access.
3. Inspect views, writable views, rules, triggers, foreign tables, extensions,
   SECURITY DEFINER routines, their owners/search paths, and callable paths
   that could write outside C1. Check access to secrets, Cron management,
   HTTP/network helpers and role-changing paths. RLS does not replace ACL checks.
4. Verify no effective INSERT/UPDATE/DELETE/TRUNCATE or ownership path to any
   existing research table, and no reachable privileged routine that provides
   equivalent writes. Check research migration tracking explicitly.
5. Compare C1 effective rights with the allowlist, including column rights,
   policies and default privileges for future objects. Unexpected PUBLIC
   TEMP/CREATE/EXECUTE rights require assessment, not silent acceptance.
6. Run positive/negative permission tests on a disposable local database only:
   C1 batch succeeds; history mutation, approval mutation, ownership mutation,
   off-cohort writes and research writes fail. Do not attempt test writes to
   existing live research tables, even inside a rollback transaction.
7. In a later authorized deployment validation, use catalog evidence and C1-only
   canaries; record the audit and repeat after relevant privilege/schema changes.

If existing inherited/PUBLIC permissions defeat isolation, deployment is blocked.
PostgreSQL has no per-role DENY that cancels a PUBLIC grant. Do not revoke or
alter existing permissions under this scope. Report the conflict for a separately
approved resolution; until then the same-project design cannot claim isolation.

Use the existing read-only C1 path and unchanged `COMPONENT1_DB_URL` to select
only proposed-cohort channel/video identity mappings. The runner already
validates the role and read-only transaction and filters videos by manifest
channels. A reviewed importer may use that path's guarded connection pattern
for channel inventory; do not modify the runner to add writes.

Validate the exported manifest hash, allowlist, deduplication and ownership
offline. Import identity/provenance into C1 only through the separate bootstrap
operator. Record the source extraction time as provenance, not as a new YouTube
statistics observation. Do not copy metric columns or history. Missing channel
rows must be reported/reconciled rather than expanding the cohort. Preserve
the proposed disabled state after import. Inventory-only bootstrap still needs
separate authorization for its database read and C1 import.

## Bounded execution and durable recovery

Supabase currently documents 256 MB memory, a 150-second Free/400-second paid
worker lifetime, 2 seconds CPU per request, and a 150-second request idle timeout.
Design below the Free limits regardless of the eventual plan.
[Official Edge Function limits](https://supabase.com/docs/guides/functions/limits).

Proposed starting bounds, subject to synthetic load validation: 60-second handler
deadline, at most four outbound attempts per invocation, 10-second HTTP timeout,
one page or 50 IDs per work item, and one database connection per worker. Stop
starting work with less than 15 seconds remaining. Cap response bytes and reject
oversized/malformed results. Persist after each item and return promptly. Do not
depend on background execution, local disk or a recursively self-invoked chain.

Use a PostgreSQL client over a TLS connection authenticated as `c1_collector`.
Prefer Supavisor transaction pooling for transient Edge workers; this remains
direct PostgreSQL protocol access, not REST. Disable prepared statements, avoid
session-dependent state, and release connections in finally blocks. Verify custom
role authentication and routing in a later connected check; never substitute the
pooler's owner login. Set transaction-local UTC, statement timeout (5 seconds),
lock timeout (1 second), and idle transaction timeout (10 seconds). No database
transaction remains open during a YouTube request.
[Official Postgres integration](https://supabase.com/docs/guides/functions/connect-to-postgres)
and [connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres).

Atomic claims use row locks on a pre-created cohort coordination row, an expiring
lease and monotonically increasing fencing token. Permit one active worker per
cohort. Every result/checkpoint commit locks and verifies the lease token and
expiry; an expired worker cannot commit after takeover. Use database time for
leases. A repeated daily invocation resolves to the same unique scheduled run.
An unfinished previous run blocks a second active run and raises an alert.

Reserve an attempt durably before each HTTP dispatch, including retries, against
the global and phase budgets. A crash may consume a reservation without a call;
this conservative accounting prevents quota overspend. Persist dispatch intent,
retry eligibility and terminal failure. Retry only transient transport/429/5xx
failures with bounded exponential backoff/jitter, at most two retries per logical
request; stop the run on credential/auth/quota failures. Persist next-attempt
time instead of sleeping across invocations. Remaining tasks stay unattempted
when a budget/deadline is exhausted.

On response completion, stamp actual UTC observation time and durably stage the
bounded response/hash under its work ID. Then atomically insert validated stats,
update inventory metadata and mark the task committed. Replaying a staged item
uses the identical timestamp and values. History conflict handling compares
canonical hashes: identical is a no-op; different content at the same key fails
validation rather than overwriting. A crash before staging may require a fresh
fetch with a fresh observation time; do not claim exactly-once API calls. A stale
worker may waste a reserved HTTP attempt but cannot write through a lost fence.

## Refresh, discovery and observation semantics

Freeze each run's starting inventory at an inventory revision. Enqueue all of
those IDs in deterministic batches of 50, with no newest-N or publication cutoff.
Reserve one initial attempt per refresh batch before starting; reject an
insufficient budget. Retry allowance cannot consume the reserve for later batches.

Phases are existing-video refresh, channel metadata/statistics refresh, fair
upload discovery, then new-candidate metadata/admission. Channel requests batch
up to 50 IDs. Discovery uses one uploads page per eligible channel per round,
persisting a rotating starting channel across runs to avoid first-channel bias
when the cap is smaller than the cohort. Persist each channel's next page token,
round position, seen-token guard and page count. Invalid/expired tokens restart
that channel within remaining budgets and are reported; do not skip an unknown
gap. Subsequent daily scans start at the newest page; interrupted-run tokens
belong to that run. Deduplicate against stable inventory.

Proposed run limits are 100 total attempts, 20 discovery attempts including
retries, and 10 pages per channel, mirroring current runner examples rather than
approved production settings. Candidate validation needs its own reserved
allowance; defer excess candidate tasks explicitly. Only admit candidates after
metadata validation proves manifest membership and agreement with the source
channel. Discovery cannot spend inventory refresh reserves. Do not use search.

Record inventory completion independently from discovery and candidate admission.
A capped scan is partial even if all existing videos refreshed successfully.
Do not infer deletion from omission. Retain admitted IDs, record unavailable
outcomes, and create no zero-valued statistics for missing videos. Missing or
hidden metrics stay NULL; a genuinely reported zero remains zero. Failed requests
mean unconfirmed IDs, not unavailable IDs. Never timestamp observations at the
scheduled time: use successful response completion time in UTC. Keep publication,
observation, receipt/staging and commit times distinct. Late observations must
not replace newer current metadata. No comment collection is included.

## Cron authentication, secrets and proposed schedule

Supabase documents periodic HTTP invocation through pg_cron plus pg_net and
recommends Vault for invocation credentials.
[Official scheduling guide](https://supabase.com/docs/guides/functions/schedule-functions).
Its current service-to-service auth examples use project secret API keys. Those
examples are not adopted: they exceed this collector's credential boundary.
Supabase also supports handler-verified external authentication when gateway JWT
verification is disabled.
[Official authentication guide](https://supabase.com/docs/guides/functions/auth).

Propose a high-entropy C1-only bearer invocation token shared between a narrowly
authorized scheduler job and the handler. Store the scheduler copy in Vault and
the handler copy as `C1_CRON_TOKEN`. The handler must validate it with a
constant-time comparison before any database/YouTube operation, reject missing
or invalid tokens, accept only bounded POST requests, and check activation gates
before claiming work. `verify_jwt=false` is acceptable only with this mandatory
custom authentication; it does not make the endpoint public. Restrict payloads
to daily-start or continuation; clients cannot supply SQL, tables, cohort IDs or
arbitrary video IDs. Duplicate invocations remain idempotent. Rotation/revocation
must update both copies; never log request authorization headers.

Future Edge secrets: `C1_COLLECTOR_DB_URL`, a YouTube key scoped for this collection,
and `C1_CRON_TOKEN`. No fallback and no reuse of `COMPONENT1_DB_URL`. Ignore any
platform-injected privileged database/API credentials; never instantiate an
admin client. Vault access is for the scheduler actor only, not `c1_collector`.
The restricted PostgreSQL connection isolates that connection's database rights
only. It does not isolate the entire Edge Function environment: platform-injected
privileged credentials may remain readable by function code, dependencies or an
attacker who compromises the worker. Ignoring those values is a code convention,
not a security boundary. No claim of complete environment-level least privilege
is made. Deployment review must explicitly assess this residual capability;
stronger isolation requires a separately approved hosting/credential boundary.
Project administrators remain a separate trust boundary. Do not place secrets
in source, SQL literals, job text, logs, error messages or browser responses.
Use sanitized codes and counts. Dependencies and authentication must be reviewed
to ensure no implicit admin-client initialization.
[Official secrets guidance](https://supabase.com/docs/guides/functions/secrets).

**PROPOSAL ONLY — DISABLED:** start daily at 02:00 Asia/Colombo (UTC+05:30),
equivalent to 20:30 UTC on the preceding calendar date; UTC cron expression
`30 20 * * *`. `scheduled_for` stores that UTC instant and the run also records
the intended Colombo collection date. Verify scheduler timezone before activation.

A separately approved continuation job could invoke the same authenticated
handler every minute during a bounded 02:00–03:00 Colombo window (20:30–21:30
UTC across the previous date). It resumes existing work only and cannot create
a daily run. Both jobs remain absent/disabled until approval; a daily start alone
cannot finish multiple bounded invocations. At window expiry, unfinished work is
partial and alerted. Cron/Vault/pg_net configuration is separate operational
setup, not part of the collector's database grants or C1 table migrations.

## Monitoring and storage

Record scheduled/start/finish/heartbeat times, selected/requested/returned/invalid/
unavailable/unconfirmed counts, unattempted tasks, retries, attempts by endpoint,
remaining budget, per-channel discovery coverage and both phase completion flags.
An HTTP 2xx or successful Cron dispatch is not collection success. Correlate Cron
run/HTTP request IDs with the C1 run, and inspect HTTP delivery outcomes separately.

Proposed alert thresholds: no daily run by 02:15 Colombo, no heartbeat for five
minutes during the active window, expired leases/repeated takeovers, any auth or
quota stop, and any incomplete run at 03:00. An independent scheduler/operator
monitor must detect missing runs even when the collector never starts. Alert
channel, owner and escalation path are unresolved; no messages are sent now.

Planning formula for one observation per entity per day: daily history rows =
channels + inventory videos; annual rows = 365 times that total. The following
are scenarios, not a fresh inventory measurement or measured PostgreSQL sizes.
Assume 150–300 bytes per history row including basic indexes, excluding WAL,
backups, bloat, staging, metadata and operational records; MB is decimal.

| Channels / videos | History rows/year | Estimated history growth/year |
|---|---:|---:|
| 18 / 1,186 | 439,460 | 66–132 MB |
| 18 / 10,000 | 3,656,570 | 548–1,097 MB |

Work outcomes for daily refresh can add roughly one entity result per video/day;
at an assumed 100–250 bytes per result that adds about 43–108 MB/year for 1,186
videos or 365–913 MB/year for 10,000. Actual JSON/index overhead may exceed this.
One 2 KB metadata row per 10,000 videos adds about 20 MB before indexes. At 100
attempts/day and a hypothetical 50 KB staged response per successful attempt,
staging alone could add 5 MB/day (1.825 GB/year). Measure with synthetic data and
later C1-only relation-size monitoring; use project-wide capacity headroom agreed
with other components. Growth increases with new inventory and extra observations.

There is no approved retention duration. Decide retention/refresh requirements
for API payloads, derived statistics, metadata, unavailable IDs, inventory
provenance, work outcomes, logs, backups and reproducible research exports with
the responsible supervisor. Stable inventory does not authorize indefinite
retention. No TTL, partition drop, automatic cleanup or approved retention
duration is defined here. Persistent staging cannot be activated without an agreed
retention and capacity plan; numeric scenarios are not policy recommendations.

History rows are append-only. `c1.guard_history` rejects every UPDATE and
TRUNCATE on `c1.channel_stats_history` and `c1.video_stats_history`, for every
role including `c1_owner`. The ethics policy requires purging data that was
deleted or made private on YouTube, so DELETE has exactly one path, and it is
the only way to delete history: a deliberate retention purge, run by a role that
holds DELETE (the owner path; the collector and model reader have none), in one
transaction that issues `SET LOCAL c1.retention_purge = 'on'` before its DELETE
statements. `SET LOCAL` ends with the transaction, so the purge cannot leak into
later work. The setting grants no privilege by itself, and no shipped script or
runtime code sets it. Each purge is a separately reviewed operator action.

# 2026-10-20 revision

## Cohort and organizations

The active proposal is `config/cohorts/component_1_derana_vs_cm_v0.3.0.proposed.json`:
41 channels, 18 Derana (`owned`) and 23 Capital Maharaja (`competitor`). Tech
Life and Auto Vision are removed; no Hiru or ITN channels. Capital Maharaja is a
holdout organization: its data must never enter model training and is used only
for competitor comparison and for testing the model on a different organization.
The v0.1.0 and v0.2.0 manifests are unchanged history.

## Data model

Organization belongs to the channel (`c1.organizations`, `c1.channels.organization_id`).
Role belongs to cohort membership (`c1.cohort_channels.role`: `owned`,
`competitor`, `generalization_test`). Both are locked after admission by
triggers. Channels and videos are one row per entity, and history is keyed by
`(channel_id, observed_at)` / `(video_id, observed_at)` only, with cohort/run as
provenance. Adding channels or a new cohort version never splits a series, and
the same channel is never stored twice for one observation. History is
append-only (`c1.guard_history`); the only delete path is the retention purge in
"Monitoring and storage". Full table, trigger
and grant details are in `research/component_1/sql/README.md`.

`organizations.is_holdout` has no default and is locked by trigger. Model code
logs in as `c1_model_reader`, which can read only two owner-rights,
`security_barrier` views: `c1.training_observations` (non-holdout organizations)
and `c1.evaluation_observations` (holdout organizations only). Their bodies are
identical except for the opposite `is_holdout` filter; a static test enforces
that. The reader has no base-table privilege, so it cannot bypass the filter.

## Collected fields (no extra quota cost)

Every list call costs one unit regardless of `part`/`fields`. The collector now
also requests video `contentDetails/duration` (stored as `duration_seconds`) and
`snippet/categoryId`, channel `snippet/country`, `snippet/defaultLanguage` and
`topicDetails/topicCategories` (Wikipedia URLs, at most 10), and playlist item
`contentDetails/videoPublishedAt` for the discovery cutoff. `search.list` is
never used.

## Bootstrap and admission

`research/component_1/sql/004_bootstrap_v0_3_0.sql` inserts only the
organizations, the pending/disabled cohort, the 41 channels with roles and the
coordination row. No videos are imported from `research` or `annotation`; the
earlier "Inventory bootstrap" section through `COMPONENT1_DB_URL` is superseded.
The first approved discovery run seeds the C1 video inventory. At that run the
collector sets `collection_coordination.admission_published_after` once, to the
run's scheduled time minus 30 days (`cohorts.admission_lookback_days`). Discovery
stops paging when an upload is older than the cutoff, and older candidates are
recorded as skipped, not admitted. Busy channels whose last 30 days exceed
10 pages (about 500 uploads) are only partly covered on day 1.

**Baseline catalogue (later, not in this change):** a separate one-time baseline
catalogue of older owned-channel videos will be needed for channel-relative
baselines that look further back than 30 days. It is not part of cohort v0.3.0
and needs its own design, budget and approval.

## Refresh policy

Each admitted video is refreshed daily for days 0–30 after publication, then
weekly until day 365, then no longer (history is kept). Weekly means the
video's age in whole days is a multiple of 7, or its last metadata observation
is older than 7 days (catch-up after a missed run). Selection runs in SQL at run
creation and `core.mjs` `refreshDue` re-checks every row. Due videos per run are
capped at 10,000 (`INVENTORY_TOO_LARGE`).

## Budgets and quota

Per run: 200 total attempts, 70 discovery, 20 candidate reserve, 10 pages per
channel. Candidates are validated in batches of 50 across channels after all
discovery pages finish (previously one task per page, which could need up to 41
attempts). Owners are checked against the immutable staged discovery responses.
Six dispatches per invocation with continuation every minute in the
02:00–03:00 Colombo window allow up to 360 dispatches, above the cap.

With U = new uploads per day across all 41 channels, daily units ≈
1 + 41–45 discovery + ceil(U/50) + ceil(31U/50) + ceil(335U/7/50) at steady state:

| U per day | Day 31 | After one year |
|---|---:|---:|
| 40 | ~72 | ~107 |
| 80 | ~104 | ~173 |
| 150 | ~156 | ~286 (over the cap) |

Upload rates are unmeasured. Refresh is spent first, so full first-page
discovery with the 20-attempt candidate reserve holds up to about 85 uploads/day
at steady state; above that discovery becomes partial, and a run whose due
